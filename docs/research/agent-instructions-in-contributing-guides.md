# How open-source projects address AI agents in contributing guides, and what we should do

Researched 2026-10-23 against primary sources only: the projects' own files fetched from
`raw.githubusercontent.com` / GitHub contents API / their own docs sites, the AGENTS.md site, and the
vendor docs of GitHub Copilot, Claude Code, Codex and Cursor. A search or a blog was used at most to
find a repo; every claim below cites the repo file or the official page. Anything not confirmed on a
primary page fetched during this research is marked **unverified**. Files were read on the default branch
on the research date; policies in this area change monthly, so dates matter.

Companion note: [`enforcing-the-contribution-flow-on-github.md`](enforcing-the-contribution-flow-on-github.md)
covers what GitHub can and cannot enforce (rulesets, CODEOWNERS, fork-safe CI). This note does not
re-derive that; section 5 only says which agent rules should land there.

**Short answer.** Three stances exist in the wild: (1) _ban_ (Gentoo, QEMU, Servo), (2) _welcome with a
human in the loop, disclosure and no autonomous submission_ (the large majority: LLVM, Rust, Node, Django,
Python, Zed, ripgrep/uv, Home Assistant, Nextcloud, Zephyr, Traefik, Mesa, llama.cpp, Ghostty), and (3)
_close the door to outside PRs_ (tldraw). Within stance 2 the practical split is: a **human-facing policy**
in CONTRIBUTING.md or a separate `AI_POLICY.md`, a **short agent-facing digest** in AGENTS.md that points to
it and adds the few rules agents miss (trailer format, never open PRs alone, never write the PR text), and a
**PR template field** the human fills. Enforcement is mostly prose plus maintainer discretion; the few
mechanical checks that exist are narrow and cheap: a PR-body checkbox parsed by CI (Django), a commit trailer
format check in the commit linter (Zephyr), a vouch bot that auto-closes PRs from unknown users (Ghostty), a
marker that a bot looks for in the diff (Zed). Our current `AGENTS.md` is written for in-house agents and
would actively mislead an outside contributor's agent (section 4.1).

## 2. Synthesis

### (a) Structure and length that works in an agent-facing file

- **Short and imperative.** The agent files that are pure policy are 10-60 lines (CPython 13, Babel 12,
  Ghostty ~35, Kubernetes ~50 with commands). The long ones are either dev-guides (Zephyr, vLLM, Astro,
  tldraw, Julia: 6-15 KB) or the unusual Rust gating protocol (13 KB). None of the policy-bearing files I read
  is 49 KB like ours.
- **Order that recurs:** (1) who this is for and which doc wins (Zephyr: "where it disagrees with the
  documentation, the documentation wins"; Wireshark: "The rules for human contributors apply to agents as
  well"); (2) the _agent-specific must/must-not list_ (trailer, no Signed-off-by, no autonomous PRs, no
  AI-written PR text); (3) commands (build, test, format, generate); (4) the "before you open a PR" checklist
  (vLLM: duplicate search, test commands, `pr-checklist` skill, "Fail-closed"; Home Assistant: run `prek`
  after a session; Nextcloud: warn when the PR is too big); (5) pointers to deeper docs.
- **Link, do not copy.** Rust's rule is the sharpest: agent files "may only link to, summarize, or
  conservatively operationalize existing human-facing documentation ... Do not make an agent file the sole
  source of a rule." Zephyr and CPython do the same. Home Assistant generates `copilot-instructions.md` from
  the PR template so the two cannot drift.
- **Say what to do when a rule fails** (Rust "STOP ... give the route", vLLM "Fail-closed", Nextcloud "Do not
  silently proceed", llama.cpp "Guide, don't solve"). Agents otherwise comply silently or ask for workarounds.
- **Limits from the tools:** Claude Code advises under 200 lines; Codex truncates combined instructions at
  32 KiB by default; Cursor says under 500 lines per rule. A rule that must be seen belongs at the top.

### (b) Disclosure conventions

- **Commit trailer `Assisted-by:`** is the de facto standard: Node, LLVM ("a commit message trailer like
  Assisted-by"), Mesa, Zephyr, Nextcloud, Traefik, Gitea, Wireshark, Vim, Julia, Ansible, UTM, Babel, Rust's
  forge policy refers to disclosure but forbids `Co-Authored-By` for agents.
  Formats seen: `Assisted-by: <agent name>` (Node), `AGENT_NAME:MODEL_VERSION [TOOL...]` (Zephyr, Nextcloud,
  Gitea, UTM), `<tool> (<model>)` (Julia), `LLM`/`Generated-by: LLM` with a level (Mesa: "Do not advertise the
  model"). Node recommends not naming for-profit brands in commit messages.
- **`Co-authored-by` for tools is banned almost everywhere it is discussed:** Node ("must not ... Sign off
  commits using ... `Co-authored-by: <agent name>`"), Mesa ("reserved for human co-authors"), Kubernetes, Zephyr,
  Gitea, Nextcloud, Babel, Julia ("this trailer replaces any co-author trailer your harness adds by default"),
  Rust. Agent harnesses add `Co-Authored-By` by default, so projects that care must say so explicitly.
- **`Signed-off-by` is human only** (Linux, Node, Nextcloud, Zephyr): it is the DCO. We have a CLA instead of
  a DCO, so the analogous rule is "the human accepts the CLA".
- **PR template field:** Django (required, exactly one of two boxes, free-text minimum), Kubernetes
  (`YES`/`NO` + how), Home Assistant ("I understand the code I am submitting and can explain how it works"),
  Zed (self-review checkbox), llama.cpp ("follow the pull request template"). The _form_ matters:
  Django's two-checkbox shape is machine-checkable; free text is not.
- **Level of disclosure:** most exempt trivial/mechanical use (Mesa, Linux "Out of Scope", Traefik, llama.cpp).
  Python makes disclosure optional ("appreciated, while not required") and still gets the same agent rules.
- **Reasons for disclosure** are stated as reviewer triage, not tracking (LLVM: "intended to facilitate
  reviews, and not to track which parts of LLVM are generated"; Linux: scrutiny "in proportion to how much of
  it was generated").

### (c) Advisory versus enforced

Of ~25 projects, the mechanisms that actually run without a maintainer reading the PR:

| Mechanism                                                                                                | Who                                                              | Cost                                   |
| -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------- |
| Parse the PR body for a mandatory disclosure checkbox and minimum words, auto-close after a grace period | Django (`pull_request_target`, base checkout only, 1-day grace)  | one Python script, one workflow        |
| Vouch bot: unknown author's PR auto-closed                                                               | Ghostty (`vouch-check-pr`, `auto-close: true`)                   | a GitHub App token + list file         |
| Commit-trailer _format_ lint                                                                             | Zephyr (`checkpatch.pl`)                                         | one regex in an existing commit linter |
| Fail the PR if a canary line is left in the diff                                                         | Zed (`danger` on `README.md`)                                    | ~10 lines of danger                    |
| Copilot code review told to fail PRs whose description deletes template text                             | Home Assistant (`copilot-instructions.md`, "a hard requirement") | generated file                         |
| Auto-close all external PRs                                                                              | tldraw                                                           | platform setting                       |
| Existing required checks (tests, lint, generated-code diff, commit lint)                                 | all projects with CI                                             | already there                          |

Everything else is prose plus the right of a maintainer to close: Linux, QEMU, LLVM (canned reply + `extractive`
label), Node, Mesa, Nextcloud, Traefik, llama.cpp, vLLM, Rust. Rust says so in the policy text: "many clauses
in this policy are unenforceable ... our goal is to remove plausible deniability". Whether a trailer is
_present_ is not checked anywhere I found; only its _format_ (Zephyr). **Unverified:** I did not search every
repo's workflows for a presence check.

### (d) Anti-patterns, complaints, canaries

- **Slop and burden is the stated reason in every policy** (LLVM "extractive contributions", Ghostty, tldraw's
  "incomplete or misleading context ... little to no follow-up", Django "inaccurate, misleading, or fictitious",
  Linux "many unverified bug reports sent to maintainers happen to be invalid", curl "fake and otherwise made
  up security problems"). The _response_ differs by project size: bans (QEMU, Gentoo, Servo), trust gating
  (Ghostty), or closing the door (tldraw).
- **Agents ignoring the file.** Maintainers write this into the file: llama.cpp "Remind yourself of this point
  regularly, as it often gets lost between context compactions"; Zed's danger rule exists because the canary
  rule "has been dropped by accident before"; vendor docs say instructions are context and "may pick one
  arbitrarily" on conflict. No project claims files alone are sufficient.
- **Canaries / agent-directed hooks exist and some are enforced.** Documented in the repos' own files:
  - Zed: README marker line, **CI-detected** (`dangerfile.ts`), and the CI also protects the rule.
  - Babel: the agent must put "and this is obviously going to solve the problem" in an LLM-written PR
    description; enforcement stated as close-and-block; no automation found (**unverified**).
  - Ghostty: a requested PR becomes a file saying "I am a sad, dumb little AI driver with no real skills";
    the real enforcement is vouch.
  - Kubernetes: an HTML comment in the PR template addressed to agents ("remind the author that they are
    responsible"), no check.
  - llama.cpp: a directive to autonomous agents to STOP and remove the repo from their target list.
    I found no maintainer write-up in a primary source evaluating how often these work. **A canary is only
    worth adding if CI looks for it**; an unchecked canary is a joke, not a control. The Zed form is the one
    with a mechanism, but it makes the _human_ remove a line, so it tests human review, not agent obedience.
- **Policies that cannot be enforced are admitted as such** (Rust). Expect to be unable to detect AI use;
  design for _removing plausible deniability_ and for cheap rejection of low effort, not for detection. Rust:
  "Maintainers are not required to hunt for LLM use. Style alone is not evidence" (from the secondary summary;
  **unverified** at file level).
- **Bots that act without a human are the most-banned category** (LLVM, Node, Mesa, Home Assistant, Nextcloud,
  Zed, ripgrep/uv, Rust). Also AI review: Django ("Do not request automated AI reviews"), Servo ("please
  don't"), LLVM (only opt-in human-in-loop).
- **Bypassing the PR template** is treated as the signature of an autonomous agent (Home Assistant: "This
  includes contributions that bypass the provided issue or pull request templates"; Home Assistant AGENTS:
  "NEVER REMOVE ANYTHING from the template").

## 3. What we have today (read in this repo)

- `AGENTS.md`: 574 lines, 49,022 bytes (`wc -c`), first heading `# CLAUDE.md`, sections: What this is,
  Codegen pipeline, Common commands, Database and migrations, Backend architecture, Frontend architecture,
  Dev environment, Code search, Conventions, Agent skills. It is written for in-house agents: "Land

- Our own commits carry `Co-Authored-By: Claude ...` trailers (`git log`), which is the opposite of the

### 3.1 Problems this causes for an outside contributor's agent

1. **`AGENTS.md` tells an agent to do things an outside contributor must not.** "Never create a branch",
   `git push origin HEAD:main`, "Land non-trivial work from its worktree", close issues, worktree creation
   in the primary checkout, "run `to-spec`/`implement-spec`" workflows. A fork contributor's agent that
   follows it faithfully will try to push to `main` (which fails) or skip the branch a fork PR needs.
2. **Size.** 49,022 bytes is above the Codex default `project_doc_max_bytes` of 32 KiB, and the file is almost
   three times Claude Code's 200-line target. Whatever is at the bottom (today: skills and the landing rules)
   may be silently dropped by Codex ("stops adding files once the combined size reaches the limit"; the exact
   truncation point inside one file is **unverified**), and the top is the only part certain to be read.
3. **Nothing asks for disclosure, understanding, or human-written PR text**, and nothing forbids autonomous
   PRs, so by default we have no basis to close a slop PR other than "does not pass CI".
4. **Claude Code reads `AGENTS.md` only without a `CLAUDE.md`** (and only from v2.1.277), and AGENTS.md is
   what Cursor/Codex/Copilot read. The memory file also says "never create CLAUDE.md". So the human-facing
   rule must not live only in `AGENTS.md`.

## 4. Proposal

### 4.1 Principles (derived from the above)

1. **One policy, written for humans, in `CONTRIBUTING.md`** (a short "AI-assisted contributions" section; a
   separate `AI_POLICY.md` only if it outgrows a screen). `AGENTS.md` links to it and adds only
   agent-operational rules (Rust's "no sole source of a rule").
2. **Put an "outside contributors" block at the very top of `AGENTS.md`** that overrides the in-house landing
   rules for anyone working from a fork, in 10-15 lines, so it survives truncation. Move the in-house landing
   rules under a heading "Maintainers' agents".
3. **Stance (decision for the maintainer):** welcome AI use; require a human in the loop who can explain the
   change; no autonomous issue/PR/comment submission; human-written PR description and replies; disclosure by
   trailer plus a PR-template checkbox; issue first for anything non-trivial. This is the median of the
   projects in section 1.
4. **Anything we need to be true must be a check**, not a sentence (section 4.4). Use the same fork-safe
   pattern as the companion note: no `pull_request_target` unless it checks out only the base and passes the
   body through `env`/a file (as Django's workflow and our `upgrade` job do).
5. **Do not rely on a canary.** If we add one, a CI step must look for it, and it must test something worth
   testing.

### 4.2 Draft: agent-facing section of `CONTRIBUTING.md`

```markdown
## AI-assisted contributions

You may use AI tools. You are the author of everything you submit and you answer for all of it.

- **A human opens the pull request.** An agent must not open issues or pull requests, post comments or
  review replies, or push to this repository on its own. Fork, branch, and let a person submit.
- **You must understand the change.** If you cannot explain what it does and how it fits the rest of the
  system without asking a model, do not submit it.
- **Write the pull request description and your replies to reviewers yourself.** Translation or grammar
  help is fine; quote any pasted model output in a `>` block and say it is AI output.
- **Disclose AI use.** Add `Assisted-by: <tool>:<model>` as a trailer to every commit where a tool produced a
  meaningful part of the diff (not for completion or formatting), and tick the matching box in the pull
  request template. Do not add `Co-Authored-By` or `Signed-off-by` for a tool.
- **Open an issue first** for anything that is not a small bug fix, and wait for a maintainer to agree on the
  approach. Large unsolicited pull requests are closed.
- **One concern per pull request.** Do not mix in refactors, renames or "improvements" the change did not need.
- **Run the checks before you push:** `mise run generate` (if you touched TypeSpec or `ent/schema`),
  `mise run check`, `mise run test`. Do not edit a test, a lint rule or a generated file to make a failure go
  away; fix the cause.
- **Unverified reports are not accepted.** If a tool found a bug or a vulnerability, reproduce it yourself
  before you report it, say that a tool found it, and write the report yourself. Security reports follow the
  security policy, not public issues.

Pull requests that ignore this may be closed without review; repeated violations lead to a block. Maintainers
decide; there is no appeal to a checklist.
```

(The last sentence mirrors Python/Node/Zed; trim if the maintainer prefers a softer tone. A "vouch" gate like
Ghostty's and a contributor ban list are heavier and listed under 4.6 as optional.)

### 4.6 Optional, heavier

- **Vouch-style gate** (Ghostty): auto-close PRs from authors not on a list. High effect on slop, high cost to
  genuine newcomers; Ghostty adds a public denounce list. Not recommended until we see volume.
- **Disabling PRs** (tldraw): only as a response to a flood.
- **Canary**: only with a CI step as in Zed's `dangerfile.ts`; otherwise skip.
- **Copilot code-review rules** (`.github/copilot-instructions.md`, generated from the PR template as Home
  Assistant does): worthwhile only if we turn on Copilot review. Django asks contributors not to request it;
  that is a policy choice.
