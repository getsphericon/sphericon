# Workspace scoping: a generated scoped client, not a context interceptor

Every Workspace-owned entity (GLOSSARY "Workspace") is reached through a **scoped client**, generated by an ent codegen template from the entities that carry the workspace mixin. `client.Scoped(ws)` returns generated wrapper types (`Query`, `Create`, `Get`, `UpdateOneID`, `DeleteOneID`) with the Workspace already applied. The Create wrapper has no `SetWorkspaceID`, so a handler cannot forget the filter and cannot name another Workspace; this holds at the type level. (A prototype on `Tag`, branch `prototype/scoped-client-tag`, showed the plain generated builders cannot give that: `SetWorkspaceID` stays callable and edge checks would live in a mutation hook.) Before this, the rule "all queries are scoped" was repeated by hand at ~174 call sites and enforced only by per-endpoint tenancy tests.

- **Create** sets `workspace_id` itself; the wrapper has no `SetWorkspaceID`.
- **References are checked too.** A scoped `Create`/`Update` verifies, for every edge to another Workspace-owned entity whose id was set, that the target belongs to the same Workspace, and fails with a typed `ErrNotInWorkspace` instead of storing a foreign id (a request body can carry any id; `SiteBroadcastsCreate` and `SiteBroadcastsUpdate` store `segmentId`/`integrationId` without an ownership check, unlike `broadcasts.SetSegment`; today nothing reads or sends through a foreign id, so this is a validation gap, not a leak).
- **The database refuses a foreign reference as well.** Every foreign key between two Workspace-owned tables (the tables of the entities that take `WorkspaceMixin`, which the manifest of kinds `ent.Kinds` lists) is composite: `(workspace_id, x_id)` references the parent's `(workspace_id, id)`, and each such parent has that unique key. An ent edge names one column, so the migration generator applies the rule to the ent schema it diffs against (`internal/infra/devdb/tenantkeys.go`): a new edge gets its composite key with nothing declared. A key whose delete action is SET NULL clears only its own column (`ON DELETE SET NULL (x_id)`, Postgres 15 and later; the Instance runs on 16 and later, `postgres.MinMajor`). The index that serves each key leads with `workspace_id`. The scoped client's check stays: it answers a write with `ErrNotInWorkspace` before it reaches the database, and the key is what holds when a raw-client path, a migration or a fixture does not ask. The edge table `contact_tags` carries `workspace_id` too: the Contact's `tags` edge reads it, and a Tag is applied or removed by writing its row through the scoped client, since the edge's setters cannot fill the column. A schema keyed on two columns gets the scoped Create, Query and Delete, and none of the by-id operations.
- **Raw `*ent.Client` is for actors whose Workspace is not known up front.** Structurally, `Handlers` in `internal/api/site`, `internal/api/external` and `internal/mcpserver` (and the collect handlers) hold no `*ent.Client`; what needs raw access lives in its own package. The raw-client packages are exactly this list, and a new entry needs a decision here:
  - `internal/accounts`: `User` (identity, credentials, profile), the Membership lookup that resolves `/w/{id}` to a scope, the Workspace row itself (the tenant root is not Workspace-owned, so it has no wrapper; `Scoped.Workspace(ctx)` is the generated read), workspace creation, and the pending Invitation lookup by token.
  - `internal/api/auth`: authentication (credentials check, API-token prefix lookup, collect-key lookup) and the construction of the external and collect scopes.
  - `internal/oauthserver`: OAuth clients, codes and token issue.
  - `internal/suspension` (Workspace suspension) and `internal/accounts` (Workspace id resolution; command-line tooling addresses a Workspace by its Workspace id).
  - `internal/events`: the bus (transactional outbox) and its subscribers (persist, suppression, automations, webhooks).
  - `internal/consent`: signed unsubscribe/confirm token handling. The Workspace comes from the token, not a login, and the code runs on the bus's raw transaction client (`bus.WithinTx`), re-scoped with `tx.Scoped(<token's Workspace>)`.
  - `internal/jobs`: job entry points, which load the row that names the Workspace (broadcast, recipient, automation run, sending domain, Workspace) and scope from it.
  - `internal/server`: tracking by recipient id (open and click), the ingest hook (the Integration key in `POST /hooks/{key}` names the Workspace), and the composition of the auth pieces above.
  - composition roots and test setup: `internal/app`, `internal/db`, `internal/testhelper`.
- **Domain modules take the scoped client too.** `automations`, `broadcasts`, `tags`, `contacts`, `outbound`, `reputation`, `messaging` (resolver, DKIM signer) and the other modules hold no raw `*ent.Client` and no bare `int64` workspace id; they receive the scoped client as an explicit parameter, so no hand-written `WorkspaceID(ws)` predicate remains outside the raw-client packages (the one exception inside them is `accounts.Scope`, which matches the Membership by `HasWorkspaceWith(public id)`). `internal/eligibility` is not a raw-client package: it takes the scoped client and passes `s.WorkspaceID()` as a bound argument inside one raw SQL expression (its correlated contact check reads the outer row's `workspace_id` column), not as a hand-written `WorkspaceID(ws)` predicate. `Scoped` is built only in a closed list of places; handlers and modules receive it and never construct it from an `int64`:
  1. site: `accounts.Accounts.Scope`, behind `Handlers.scopedFor` / `scopedWithRoleFor`;
  2. external and MCP: `ExternalSecurityHandler.HandleBearerAuth` (the token's Workspace), read with `auth.TokenScoped(ctx)`;
  3. collect: `CollectSecurityHandler` (the collect key's Workspace);
  4. job entry points and event subscribers, from the loaded row's Workspace (`internal/jobs`, `events.Persist`/`Suppress`). `EvaluateTriggerWorker` loads its contact and scopes from it; `DeliverWebhookWorker` loads its endpoint and needs no further scoped read. The webhooks consumer holds only an event envelope (a Workspace id), so the bus subscriber is the raw-client entry that builds the scope it passes to `jobs.Client.Dispatch`;
  5. transaction re-scoping, the same Workspace over a transaction's client: `events.Bus.WithinScopedTx` and the invitation accept in `accounts`;
  6. a Workspace named by a secret rather than a login: the Integration key of the ingest hook (`POST /hooks/{key}`, ADR 0037), the signed unsubscribe/confirm token (`internal/consent`), and the bootstrap token (`accounts.BootstrapScope`, the oldest Workspace).
- **The generated wrapper covers what production uses,** not just CRUD: conditional bulk `Update().Where`/`Delete().Where` (broadcast claim, outbound lease fencing), `OnConflict` upserts, `CreateBulk` and `GroupBy`. Anything the template cannot express is a named raw-client path.
- **Known hole: an entity returned from a scoped read still carries the raw client.** `own.Update().SetWorkspaceID(other)` and `own.QueryContacts()` bypass the wrapper (prototype-verified). Closing it with distinct DTO types was rejected as too much generated code; it is covered by a repo-wide check (the analyzer `entityupdate`, `tools/analyzers`) banning entity-level `Update()`, test code included, with no exclusions. Update by id (`s.Tag().UpdateOneID(id)`). The check reads what is an entity, and which of its methods starts a write, from the manifest of roles the generator declares in `ent` (`TypeOf_<Type>`, `RoleOf_<Type>_<Method>`), not from a type's name, so an entity named like a builder suffix (`OAuthClient`) is caught like any other; `ent/schema/roles_test.go` holds the manifest's entities to the types whose `Update` returns their own `<Entity>UpdateOne`. `QueryXxx()` on a loaded entity (read-only) is not covered.
- **`OAuthCode` is Workspace-owned.** It takes `WorkspaceMixin` like every other Workspace-owned entity (#1364): the consent creates a code through the scope of the Workspace the User was admitted to, and the code exchange reads the code by its secret with the raw client (`oauthclients`, a raw-client package) and claims it through the scope of the Workspace the row names, as the other entries named by a secret do. A code of one Workspace therefore cannot name a Membership of another, nor be claimed through another's scope. Workspace-owned means `WorkspaceMixin` and nothing else: the generation (`internal/entgen`) refuses a `workspace_id` declared outside it unless it says why it does not make its entity Workspace-owned (`schema.NotWorkspaceOwned`).
- **External broadcast create/update inputs carry no segment or integration.** The external equivalent is `broadcasts.SetSegment`, which rejects a foreign segment; the `ErrNotInWorkspace` validation gap above is therefore a site-API concern.
- The time-mixin migration also set `DEFAULT CURRENT_TIMESTAMP` on the existing `created_at`/`updated_at` columns of the other tables, not only on the four added `updated_at` columns.
- Schemas share a `WorkspaceMixin` (`workspace_id` plus the `workspace` edge) and a `TimeMixin` (`created_at`, `updated_at`, on every entity including append-only ones, for uniformity).

## Considered options

- **ent interceptor / privacy policy reading the Workspace from `context`.** Rejected: the scope is hidden state in `ctx`, and the legitimate unscoped actors above need bypass flags that become the place bugs live. It also adds the Intercept and Privacy codegen features, which change every generated builder.
- **Plain generated builders returned from `Scoped`.** Rejected after the prototype: smaller, but `SetWorkspaceID` remains and the reference check becomes a hidden mutation hook.
- **Hand-written wrapper per entity.** Rejected: ~22 shallow wrappers with no logic, and a new entity silently has none.
- **Per-entity modules only (each takes `workspaceID`).** Kept as a follow-up on top of this, not a replacement: they take the scoped client instead of an `int64` and stop repeating the filter.
- **Composite foreign keys declared in the ent schema.** Not possible: an ent edge names one column (ent v0.14). The keys are composite all the same, applied by the migration generator from the ent schema (above).
- **Row-level security.** Not taken. Its policy reads the Workspace from a session setting, the same hidden state in `ctx` rejected above, and the actors that legitimately work across Workspaces (the raw-client list) would need a role or a bypass of their own. It filters which rows a query sees but does not check where a reference points; the composite keys do that.

## Consequences

- One isolation test at the scoped-client seam covers every mixin entity; the list is taken from the generated code, so a new entity is covered without editing the test.
- The codegen pipeline gains a step (`ent/template/scoped*.tmpl` via entc), documented in docs/agents/codegen.md.
