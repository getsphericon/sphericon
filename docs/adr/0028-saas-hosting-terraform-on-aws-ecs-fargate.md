# The SaaS runs on AWS (ECS Fargate, RDS, SES), provisioned only through Terraform

The hosted offering (Sphericon, `getsphericon.app`) is described entirely in Terraform under
`infra/`: nothing is created by hand in the console or through an MCP server. The application
shape: one service (HTTP, river and watermill in one process, no worker), migrations applied once
before new instances start with `AUTO_MIGRATE` unset, no transaction-mode pooler (river uses
LISTEN/NOTIFY), `ENCRYPTION_KEY` generated once outside Terraform and never rotated, secrets never
in plain text in a task definition, a plan or a log. One root module, one environment
(production: a test deployment destroyed and recreated freely, so no deletion protection and no
standby).

## Decisions

- **One AWS account, region `us-east-2`** (US-first audience), everything in it: compute,
  database, DNS, email, secrets, state. Operator access is the `sphericon` CLI profile from
  `aws login` (session credentials); no long-lived keys are stored anywhere.
- **Plain ECS on Fargate (ARM64) behind an Application Load Balancer.** App Runner is closed to new
  customers. ECS Express Mode (`aws_ecs_express_gateway_service`) was evaluated and rejected: it
  owns its load balancer and exposes no listener rules, so it cannot express the three hosts or the
  API path rewrite. The ALB routes by `Host`: the apex `getsphericon.app` (SPA and `/site/*`; `APP_URL` is
  `https://getsphericon.app`), `api.getsphericon.app` (rewritten to the `/api` prefix by a
  listener-rule URL transform) and `t.getsphericon.app` (`/t.js` and `/collect/*` only). Anything
  else is a 404. One ACM certificate with the three hosts as names, validated by DNS in Route 53.
  Task: 0.5 vCPU / 1 GB, one task, rolling deploy (new task first, circuit breaker with
  rollback), health check `/readyz`.
- **No NAT gateway** (cost): tasks run in public subnets with public IPs and a security group that
  admits only the load balancer; the database is in subnets with no internet route and admits only
  the tasks. The task execution role writes logs and reads the two secrets; the tasks have no task
  role.
- **RDS PostgreSQL 18**, `db.t4g.micro`, single AZ, gp3 20 GB, encrypted, not publicly accessible.
  The password is generated by Terraform (`random_password`) and never typed.
- **Secrets Manager, injected by ECS** through the task definition `secrets` (`valueFrom`, one JSON
  key each), so values never pass through Terraform variables or container definitions.
  `sphericon/app` (`JWT_SECRET`, `ENCRYPTION_KEY`, `BOOTSTRAP_TOKEN`, optional `LICENSE_KEY`) is
  created once by `mise run infra:bootstrap` and never touched by Terraform, which reads only its
  ARN. `sphericon/runtime` (`DATABASE_URL`, the SES key) is composed by Terraform: the app reads one
  `DATABASE_URL`, and ECS cannot assemble a URL from parts. Those values are therefore in the state.
- **A separate product domain, `getsphericon.app`, wholly managed by Terraform.** The whole domain
  is a Route 53 hosted zone; the registrar's nameservers are pointed at it once, by hand.
  `getsphericon.com` stays outside Terraform: it keeps the marketing site and Google Workspace
  mail. Why a second domain: product mail reputation and cookies are isolated from the marketing
  site and Google Workspace; the apex can be an ALIAS to the load balancer with no conflicting
  records (a marketing apex and mail records would clash); and `.app` is on the browser HSTS
  preload list, so HTTPS is enforced from the first request.
- **SES in `us-east-2`**: a domain identity for `getsphericon.app` with Easy DKIM and a MAIL FROM
  subdomain (`mail.getsphericon.app`, MX and SPF there only; SES needs no SPF at the apex, DMARC
  passes through the aligned DKIM), DMARC `p=none` at `_dmarc`, all in Route 53;
  `SYSTEM_EMAIL_FROM` defaults to `noreply@getsphericon.app`. The
  app's SES provider signs with static keys, so Terraform creates a send-only IAM user and stores
  its key in `sphericon/runtime`. A new SES account is in the sandbox; production access is a
  manual request.
- **Migrations before new tasks.** ECS has no pre-deploy hook, so a `terraform_data` step runs the
  migrate task definition (`sphericon migrate`) with `aws ecs run-task`, waits, and fails the apply
  on a non-zero exit; the service depends on it and is left on the old revision when it fails. On
  the first apply the database, the secrets and the network exist before it runs and the service
  is created after it. It re-runs whenever the migrate task definition changes (a new image tag).
  It needs the `aws` CLI and credentials in Terraform's environment, which `mise run infra`
  provides.
- **State** is an S3 bucket in `us-east-2` (versioned, encrypted, public access blocked, TLS only)
  with native locking (`use_lockfile`, no DynamoDB). It is created once by the idempotent
  `mise run infra:bootstrap`, because a backend cannot create its own storage. It is private and
  encrypted because the state holds the database password, the composed `DATABASE_URL` and the SES
  key.
- **The image is public on GHCR**, published by the existing release workflow (goreleaser, multi-arch
  `ghcr.io/getsphericon/sphericon`). ECS pulls it anonymously, so there are no registry credentials. The
  package must be made public once by hand (not possible through Terraform), and an image only
  exists after the first release.
- **The AWS MCP server is for read-only inspection.** Every change goes through Terraform.

## Considered Options

- **ECS Express Mode.** Rejected: no host rules or URL rewrite (above).
- **App Runner.** Closed to new customers.
- **EKS.** Rejected: a control plane and nodes cost more and add operations for one service; the
  Helm chart stays for self-hosters.
- **Lambda or a single EC2 host.** Rejected: river and watermill need a long-lived process, and
  an instance means manual patching and deploys.
- **RDS-managed master password.** Rejected: the app needs a `DATABASE_URL`, which would still
  have to be composed from it; the Terraform-generated password gives the same state exposure
  without a second source.

## Consequences

- **Cost** is about $55-60 a month: the ALB (about
  $18), Fargate ARM (about $14), RDS with storage (about $14), public IPv4 addresses for the ALB
  and the task (about $11), plus Route 53, Secrets Manager and logs (a few dollars). The ALB is
  the largest fixed item.
- **Connections.** `db.t4g.micro` allows `LEAST(DBInstanceClassMemory/9531392, 5000)`, about 85-110
  (read the real value with `SHOW max_connections`). Each process opens two pools; they are set to
  10 + 10, so old plus new task during a rolling deploy is 40 and the migrate task adds about 4.
  Beyond one permanent extra process the pools or the instance class must change.
- **Tasks in public subnets** are reachable only through the security group; the cost is a public
  IPv4 charge per task and no private egress. Adding a NAT gateway or VPC endpoints later moves
  them private.
- **`terraform_data` with `local-exec`** couples apply to the AWS CLI and live credentials; a
  failed migration fails the apply instead of leaving a half-rolled deploy.
- **Open risk: customer CNAME tracking domains**. Per-tenant domains and
  certificates need a different edge (an ALB holds up to 25 certificates; CloudFront or Caddy
  with on-demand TLS beyond that). A separate decision.
