# Sphericon roadmap

Updated 2026-11-08. This roadmap covers the on-premise product.

The next stage makes the existing product demonstrably usable: an administrator can install,
upgrade and recover an Instance, and a marketer can complete each advertised workflow on it.
Automation conditions and branching are the first proposed capability expansion.

## How to read this roadmap

- Status: `planned` · `in-progress` · `done`. All acceptance initiatives below are `planned`:
  inspecting code, documentation or existing tests does not complete their acceptance.
- IDs are stable. The order below is a proposed order of execution; `Depends on` names prerequisites
  for acceptance, not dependencies on rebuilding features that already exist.
- Each acceptance initiative produces a scenario checklist, execution evidence, defect links and
  the outcome of retesting fixes. Record the app release or commit, environment, browser and
  provider where relevant. Link the resulting report from its row.
- Review current contracts and implementation before writing each checklist. Older capability
  descriptions and completion labels are not acceptance evidence.
- A feature is accepted after its normal path, failure paths, permissions and relevant restart or
  retry behaviour have been exercised. Fix blocking defects and bring its instructions into line
  with the observed behaviour before marking the initiative `done`.

## Extend Automations

| ID  | Initiative               | Outcome                                                                                         | Scope                                                                                                                                                                                                                                                                          | Depends on | Status  | Links                                                                                                                      |
| --- | ------------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- | ------- | -------------------------------------------------------------------------------------------------------------------------- |
| R12 | Conditions and branching | A marketer sends Contacts through different paths according to their current data or behaviour. | Start with an if/else decision using the existing Condition language. Specify when it is evaluated, Event-property context, path convergence, versioning, editor validation, restart behaviour and reports. First agree the model and acceptance scenarios; then implement it. | R4, R6     | planned | [Current linear contract](https://github.com/getsphericon/sphericon/blob/main/typespec/external/resources/automations.tsp) |

The following are candidates for the next Automation initiatives. Their priority and scope remain
to be decided; they are not missing implementations of an already accepted spec.

- **Wait for an Event or Condition, with a timeout.** Example: wait up to two days for a purchase;
  choose the next path according to whether it happened. Define observations arriving during a
  wait, restarts, late Events and the timeout race.
- **Repeat Enrollment.** Example: run a post-purchase sequence after each order. Define repeat
  entry after completion or failure, concurrent Enrollment, cooldown and Event deduplication.
- **Calendar and date-based entry and waits.** Birthdays, anniversaries, recurring schedules and
  the Contact's local sending window. Define time zones, daylight-saving changes, absent dates
  and the relationship to repeat Enrollment.
- **Additional Actions.** Set or clear a Custom field, record an Event, and enroll in another
  Automation. Tag changes and HTTP calls already exist; cross-Automation Enrollment already exists
  as a Rule Action. Define composition and cycle prevention before adding another entry path.
- **Simulation and diagnostics.** Preview a Contact's path, explain each decision and wait, and
  exercise a scenario before publishing without delivering messages.
- **Experimentation.** Random splits and A/B variants with stable assignment and meaningful
  outcome reporting, after deterministic branching is accepted.

## Other capability candidates

- Continue the agreed Channel sequence: [web push](https://github.com/getsphericon/sphericon/issues/1102),
  then WhatsApp, then mobile push. Give each Channel its own implementation and real-provider or
  real-device acceptance, following the [Channel map](https://github.com/getsphericon/sphericon/issues/916).
- Measure segmentation, audience resolution and delivery throughput at declared audience sizes;
  publish measured limits and address the bottlenecks found.
- Choose native connectors and reusable marketing playbooks from concrete on-premise use cases.

Promote a candidate into the ordered table only after agreeing its user outcome, boundaries and
prerequisites. Detailed design belongs in this repository's ADRs and issues.
